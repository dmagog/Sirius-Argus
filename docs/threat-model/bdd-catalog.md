# Sirius Argus — BDD-каталог сценариев

> Каждая угроза = поведение; контроль = ответное поведение системы. Каждый сценарий служит сразу четырём целям: **Модель Угроз**, **acceptance-тест** (pytest-bdd против живой системы), **шаг демо**, **строка карты покрытия**.
>
> Теги: `@<категория>` · `@OWASP-MLxx` / `@ATLAS-<tactic>` · `@P0|P1|P2`. Персоны (A1–A21) — из [personas.md](personas.md); оценка риска — [risk-register.md](risk-register.md). Статус всех сценариев — `spec`.

## Конвенции

- **P0** — обязателен в демо (money-shot). **P1** — низковисящий фрукт. **P2** — practice-maxxing / частично-остаточный.
- Каждый `.feature` = категория; `Scenario` = строка таблицы. `Then`-клаузы — поведение, которое система **обязана отработать**.
- ID сценариев — **две цифры** (`SUP-01`); ID рисков в [risk-register.md](risk-register.md) — **одна цифра** (`SC-1`). Префиксы `DATA`/`SC`/`RB` встречаются и там, и там — различать по числу цифр.

## Сценарии (Gherkin) — контур контроля (новые)

```gherkin
@ci-supply-chain @ATLAS-execution @P0
Feature: Защита CI/build-конвейера
  Scenario: CI-01 — Отравленный шаг пайплайна не проходит
    Given пайплайн использует базовый образ без пина или нестандартный шаг
    When запускается CI на PR
    Then шаг с неподписанным/неприкреплённым образом не выполняется
    And создаётся Finding(type=ci-supply-chain)
    And раннер работает с минимальными правами, без доступа к прод-секретам
```

```gherkin
@availability @ddos @P1
Feature: Устойчивость к распределённому DDoS
  Scenario: DOS-01 — Объёмный флуд не роняет платформу
    Given внешние поверхности (serving-gateway и control-plane) стоят за reverse-proxy
    And заданы global и per-IP rate-limit, лимиты соединений и таймаутов
    When приходит объёмный флуд с множества источников
    Then избыточные запросы отбрасываются быстро (429/503, load-shedding)
    And ядро остаётся доступным для легитимного трафика
    And создаётся Finding(type=ddos) и поднимается алерт
    And объёмная L3/L4-защита (upstream scrubbing) зафиксирована как остаточный риск
```

```gherkin
@identity @ATLAS-credential-access @P0
Feature: Стойкость к краже токенов
  Scenario: CRED-01 — Утёкший или повторно использованный токен отвергается
    Given сервисный токен с коротким TTL и узким scope
    When токен используется после истечения TTL или вне своего scope
    Then запрос отклоняется
    And создаётся Finding(type=token-misuse) с привязкой к субъекту
    And событие фиксируется в аудите
```

```gherkin
@registry-integrity @P0
Feature: Целостность реестра моделей
  Scenario: REG-01 — Прямой тамперинг метаданных реестра пресекается
    Given актор пытается изменить флаг prod-approved/стадию напрямую в MLflow
    When запись идёт мимо Control Plane
    Then сетевая политика отклоняет прямое подключение к MLflow
    And попытка фиксируется как Finding(type=registry-tamper)
    But даже при успешной записи integrity-проверка CP выявляет расхождение
```

```gherkin
@access @authz @P0
Feature: Объектная авторизация
  Scenario: ESC-01 — IDOR / эскалация привилегий отклоняется
    Given актор с ролью DS аутентифицирован
    When он запрашивает чужой объект или действие уровня MLSecOps по прямому id
    Then доступ отклоняется на уровне объекта (не только маршрута)
    And попытка эскалации в аудите с was_authorized=false
```

```gherkin
@ML09 @toctou @P1
Feature: Целостность артефакта до загрузки
  Scenario: TOCTOU-01 — Подмена артефакта после скана ловится
    Given артефакт прошёл скан и подписан
    When артефакт в хранилище подменён до загрузки в сервинг
    Then admission-control при загрузке ре-верифицирует подпись/хеш
    And несоответствие блокирует загрузку
    And создаётся Finding(type=artifact-tamper)
```

```gherkin
@ML02 @feedback-loop @P2
Feature: Целостность петли дообучения
  Scenario: FB-01 — Отравление онлайн-данных дообучения детектится
    Given модель периодически дообучается на прод-данных
    And атакующий систематически вливает смещающие примеры
    When собирается обучающая выборка следующего цикла
    Then проверяется provenance и распределение источников
    And аномальный вклад источника помечается Finding(type=feedback-poisoning)
    And подозрительная порция исключается из обучения до ревью
```

```gherkin
@self-supply-chain @P1
Feature: Безопасность зависимостей платформы
  Scenario: SC-01 — CVE в зависимости самой платформы ловится
    Given в зависимостях control-plane/сканеров есть пакет с известной CVE
    When CI гоняет скан зависимостей платформы (не только модели)
    Then гейт помечает находку и блокирует сборку
    And создаётся Finding с привязкой к компоненту платформы
```

```gherkin
@governance @rollback @P1
Feature: Запрет небезопасного отката
  Scenario: RB-01 — Rollback на уязвимую версию блокируется
    Given в проде версия N; версия N-1 имеет открытый Finding
    When запрашивается откат на N-1
    Then откат блокируется version-policy
    And требуется явный аппрув MLSecOps с обоснованием в аудите
```

```gherkin
@availability @denial-of-wallet @P2
Feature: Защита от истощения ресурсов
  Scenario: DOW-01 — Флуд инференса троттлится и квотируется
    Given на ключ задан лимит запросов и квота ресурсов
    When ключ превышает лимит/квоту
    Then избыточные запросы отклоняются (429)
    And создаётся Finding(type=resource-exhaustion)
```

```gherkin
@visibility-integrity @P1
Feature: Целостность слоя видимости
  Scenario: VIS-04 — Смена статуса сработки контролируется
    Given Finding в статусе open
    When актор без прав MLSecOps пытается перевести его в FP
    Then действие отклоняется
    When MLSecOps меняет статус с обоснованием
    Then изменение применяется и фиксируется в аудите (кто/когда/почему)
```
