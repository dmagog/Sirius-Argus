# ADR-0013: Интеграция с сервисами обучения — control-plane как точка контроля

- Статус: Accepted (опирается на [ADR-0001](0001-mlflow-wrapped.md), [ADR-0002](0002-gitea-control-plane-ci.md), [ADR-0005](0005-fail-closed-protect-enforcer.md), [ADR-0006](0006-model-signing-provenance.md))
- Дата: 2026-06-03

## Контекст
Control-plane — слой **контроля и governance**, а не тренировочная платформа: обучение исполняют внешние сервисы (CI-джоб, MLflow Project, Kubeflow/Airflow-шаг, managed — SageMaker/Vertex). Сам тренинг (компьют, изоляция, оркестрация) — вне нашей границы. Но процесс обучения нужно **контролировать**: чтобы в прод уходили только модели из проверенных данных, с зафиксированным происхождением, прошедшие скан артефакта, подпись и policy-гейт. Значит нужен **явный контракт интеграции** между внешним тренером и control-plane, а не доверие «тренер сам всё сделает правильно».

## Решение
Control-plane — **единственная точка контроля и system-of-record** вокруг обучения. Внешний тренер интегрируется через **фиксированный API-контракт (handshake)** и НЕ пишет в реестр/прод в обход. Контрольные точки уже существуют — ADR лишь описывает, как тренер в них встраивается.

### Процедура (handshake, по шагам)
1. **Pre-train — выдача санкционированного датасета.** Тренер (под сервис-аккаунтом) запрашивает версию датасета: `GET /api/datasets/{id}` + `/schema`. Отдаются только **admitted** (не `quarantined`, прошедшие DATA-гейт: trusted-source `DATA-01`, качество/метки `DATA-02/03`), с учётом допуска к `sensitivity` (object-level authz, PII-маскирование `DATA-04`). **Обучение на карантинном датасете не санкционируется.** Тренер получает `dataset_version_id` как handle происхождения.
2. **Train — снаружи, вне нашей границы.** Тренер обучает на санкционированной версии и **обязан зафиксировать происхождение**: `code_commit`, `env_lock` (lock окружения), `dataset_version_id`.
3. **Post-train — возврат через гейт.** Результат заводится только так:
   - артефакт модели → `POST /api/models/{id}/ingest` — **ингест-гейт `SUP-01`**: скан байтов в карантине **без десериализации**; вредоносный → блок `422` + `Finding(critical)`, в реестр не попадает; чистый → карантин-MinIO + версия `stage=dev` с `artifact_hash`;
   - метаданные/lineage версии → `POST /api/models/{id}/versions` (`dataset_version_id` + `code_commit` + `env_lock` + `intended_use`/`limitations`). Критичность `regulatory/financial` → `requires_validation=true`.
   Без прохождения гейта и без lineage версия в реестре/проде не появляется.
4. **Sign-after-scan.** `POST /api/models/{id}/versions/{v}/sign` — подпись реальных байтов через OpenSSF model-signing (`SUP-04`, [ADR-0006](0006-model-signing-provenance.md)).
5. **Promote — только через policy-гейт.** `POST .../promote`: единая точка входа, fail-closed; критичные → ручной аппрув + separation of duties + verify-on-consume подписи (`VIS-03`/`GOV-01`). **Тренер промоутить сам не может.**
6. **Audit.** Каждый шаг (выдача датасета, ingest, sign, promote, отказы) — в append-only аудит с hash-chain (`LOG-02`/`MON-04`).

### Чем обеспечивается контроль (а не «надежда на послушность»)
- **Сетевой/архитектурный энфорсмент:** реестр (MLflow) доступен только через control-plane ([ADR-0001](0001-mlflow-wrapped.md)); карантин-стор и прод — за единой точкой входа ([ADR-0005](0005-fail-closed-protect-enforcer.md)). Прямой пуш тренера в реестр/прод закрыт сетью и authZ, а не правилами на бумаге.
- **Сервис-аккаунт тренера** (Keycloak, как у serving): минимальные права — `dataset.read`, `model.ingest`, `model.version`; **без** `promote`/`prod.*`. То есть тренер физически не может миновать ручной аппрув-гейт.
- **Обязательные гейты:** ingest-скан и lineage — условие появления версии; подпись и policy-гейт — условие прода.

### Точки интеграции (API-контракт)
| Шаг | Эндпоинт | Право (RBAC) | Контроль |
|---|---|---|---|
| датасет | `GET /api/datasets/{id}`, `/schema` | `registry.read` | DATA-01/04, object-level authz |
| ingest артефакта | `POST /api/models/{id}/ingest` | `model.ingest` | SUP-01 (скан без десериализации) |
| версия + lineage | `POST /api/models/{id}/versions` | `model.version` | MON-02 |
| подпись | `POST .../{v}/sign` | `model.sign` | SUP-04 |
| промоушен | `POST .../promote` | `promote` (ручной аппрув-гейт) | VIS-03/GOV-01, verify-on-consume |

Write-through в MLflow (теги lineage/критичности) — fail-soft, control-plane остаётся источником истины.

### Как подключаются конкретные тренеры
- **CI-джоб** (Gitea webhook → control-plane как CI, [ADR-0002](0002-gitea-control-plane-ci.md)) — уже есть; тренинг-шаг просто зовёт контракт выше.
- **MLflow Project / Kubeflow / Airflow-шаг / managed (SageMaker, Vertex)** — любой оркестратор вызывает тот же API под сервис-аккаунтом. Платформа обучения остаётся выбором команды; контур контроля — один.

## Последствия
- (+) Контролируем обучение, не исполняя его: чёткая граница ответственности; переиспользуем существующие гейты (ingest/lineage/sign/promote/аудит); тренинг-стек заменяем без изменений в контуре.
- (+) На защите — сильная позиция: «control boundary», а не «ещё одна MLOps-платформа».
- (−) Контракт работает, пока тренер ходит через API; для «непослушного» тренера защита держится на **сетевой изоляции + authZ** (прямой доступ к реестру/проду/карантину закрыт), а не на доверии.
- (−) Полную защиту от «отравленного, но не вредоносного» артефакта скан не даёт (предел статанализа, `SUP-06`) → для критичных обязателен ручной аппрув-гейт.

## Альтернативы
- **Исполнять обучение в control-plane** — отклонено: не наш слой; вес/ARM/cold-start; размывает фокус на безопасности.
- **Доверять тренеру прямой пуш в реестр/прод** — отклонено: обходит ingest-скан, lineage, подпись и ручной аппрув-гейт; ломает единую точку входа.
- **Только организационная политика (без энфорсмента)** — отклонено: контроль должен быть технически принудительным (сеть + authZ + fail-closed гейты).
