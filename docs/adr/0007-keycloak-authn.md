# ADR-0007: AuthN через Keycloak (OIDC) — заменяет ADR-0003

- Статус: Accepted (supersedes [ADR-0003](0003-no-keycloak-inapp-rbac.md))
- Дата: 2026-06-01

## Контекст
ADR-0003 предлагал самописный RBAC в control-plane. Катать свой auth в платформе безопасности — антипаттерн: лишний риск и слабый сигнал для судей. Keycloak даёт зрелый OIDC/OAuth2, управление пользователями, роли/группы; настройка для нашего скоупа невелика (импорт realm JSON); в `main` у команды Keycloak уже развёрнут — конвергируем, а не изобретаем.

## Решение
- **AuthN и идентичность — Keycloak** (OIDC): логин, выдача и валидация JWT, пользователи, роли/группы (DS/DE/MLSecOps/Product/CEO), сервисные identity для CI и воркеров.
- **Object-level authZ — в control-plane.** Keycloak даёт роль/группу, но «может ли актор трогать ИМЕННО этот объект» — логика приложения; это и закрывает `ESC-01`/IDOR. То есть authN отдаём Keycloak, а тонкую объектную авторизацию держим у себя.
- Realm импортируется JSON-ом (воспроизводимо, без ручных кликов). Keycloak — во внутренней сети; наружу доступ только через control-plane / reverse-proxy.

## Последствия
- (+) зрелый authN без самописного auth; узнаваемо судьями; конвергенция с `main`.
- (−) +1–2 контейнера (Keycloak + его БД), JVM-вес (RAM); Keycloak — новая поверхность атаки и SPOF для authN (см. риск-реестр). Митигация: compose-профиль, realm-as-code, не выставляем наружу.

## Альтернативы
- Самописный RBAC (ADR-0003) — отклонён (не катаем свой auth).
- Authentik / Zitadel — Keycloak выбран из-за наличия в `main` и знакомости судьям.
