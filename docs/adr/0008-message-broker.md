# ADR-0008: Межсервисное взаимодействие — лёгкий брокер (шина событий + очередь сканов)

- Статус: Accepted
- Дата: 2026-06-01

## Контекст
Нужна ясная модель взаимодействия сервисов и развязка, чтобы не плодить синхронный API-меш («все дёргают всех»). Сканы артефактов долгие — их нельзя выполнять внутри HTTP-запроса. И каждое значимое действие должно уходить в событие (для аудита, карты покрытия, логов — см. ADR-0009).

## Решение
- **Лёгкий брокер — Redis Streams** (одна лёгкая нода; заодно бэкенд rate-limit для `RT-01`/`DOS-01`). Не Kafka.
- **Async-очередь сканов:** control-plane кладёт задачу → воркеры `security/` забирают → публикуют `Finding`. Запрос не блокируется.
- **Шина событий:** каждое значимое действие публикует событие; потребители — аудит-логгер, карта покрытия, алерты, отгрузка логов в лог-стор.
- **Синхронно (HTTP) остаётся:** прямые чтения control-plane → MLflow/MinIO/Gitea. В брокер их НЕ тащим — иначе оверинжиниринг.

## Последствия
- (+) ясная модель (sync-чтения vs async-события), развязка компонентов, фундамент observability; сканы не блокируют запросы.
- (−) +1 контейнер; брокер — инфра-зависимость и потенциальная цель (инъекция/подмена событий) → ACL топиков, аутентификация клиентов, критичные события дублируются в tamper-evident аудит.

## Альтернативы
- **NATS** — отличная лёгкая альтернатива; Redis выбран как минимальный и уже полезный под rate-limit.
- **Kafka** — оверкилл для ноутбука.
- Чистый синхронный HTTP — не решает долгие сканы и плодит API-меш.
