# Sirius Argus — Итеративный план реализации (roadmap)

> Как строим: тонкими вертикальными срезами. Каждая итерация поднимается через `docker compose up` и **«зажигает» свой набор BDD-сценариев** зелёными — это её Definition of Done. Любая итерация — валидная точка остановки: на каждой границе есть рабочая демонстрируемая система.
>
> Порядок следует **приоритетам куратора** и риск-реестру ([ADR-0005](adr/0005-fail-closed-protect-enforcer.md)): сначала реестр и контур контроля + build-time гейты; рантайм — позже (у куратора тоже T5). Сценарии — из [bdd-catalog](threat-model/bdd-catalog.md); маппинг приоритетов → контроли — в [README](../README.md).

## Итерации

### И0 — Walking skeleton
- **Приоритет куратора:** скан кода (T1, старт).
- **Строим:** `docker-compose` (Postgres, MinIO, MLflow во внутр. сети, Gitea, reverse-proxy, заглушка control-plane на FastAPI); сетевая изоляция (наружу только control-plane и serving-gateway); каркас object-authz и fail-closed; pre-commit + SAST на нашем же коде с первого дня (догфуд).
- **Зелёные сценарии:** `ACC-05` (authN на всех маршрутах), базовый `RT-06` (netpolicy).
- **DoD:** `docker compose up` поднимается, дашборд открывается, логин под ролью пишется в аудит.

### И1 — Реестр + роли + история + lineage (ядро MVP)
- **Приоритет куратора:** реестр моделей (T1); версионирование, история, связка данные-код-модель, ролёвка (T3).
- **Строим:** control-plane-реестр поверх MLflow; **схема модель-карты / профиля безопасности**; zero-trust RBAC (object-level) + sensitivity-доступ; `AuditEvent` + **hash-chain** (tamper-evidence); граф lineage датасет→код→модель→деплой + **запрос blast-radius** (кого затронет плохой dep/датасет); хеш-версионирование артефактов и датасетов.
- **Зелёные сценарии:** `ACC-01/03/04/05`, `ESC-01`, `CRED-01`, `MON-04` (подмена аудита), `MON-02` (воспроизводимость).
- **DoD:** регистрация модели end-to-end, ролевые вью, аудит-таймлайн, видимый lineage с blast-radius.

### И2 — Скан моделей + gate на закачку + сканы данных + скан кода
- **Приоритет куратора:** скан моделей (T2); сканы данных, security gate на закачку (T4); автоконвертация/запрет форматов (T5); скан кода (T1).
- **Строим:** библиотека `security/` (modelscan/picklescan + Trivy); сущность `Finding` + триаж; ingestion-гейт (карантин→скан→admit/reject) для моделей и датасетов; **политика форматов** (pickle→safetensors или отклонить); **ML-aware SAST** (правила под `pickle.load`/`torch.load`/`eval`/ноутбуки); **скан архивов датасетов** на вредоносные файлы.
- **Зелёные сценарии:** `SUP-01` (showpiece — вредоносный pickle блокируется), `SUP-07` (формат), `DATA-01/02/04`, `CODE-01` (SAST), `VIS-02` (триаж фолза).
- **DoD:** вредоносная внешняя модель блокируется до загрузки; страница сработок; формат-политика и скан данных работают.

### И3 — Единая точка входа в прод + подписи + policy-гейт
- **Приоритет куратора:** security gate перед продом (T2); подписи (T4).
- **Строим:** Gitea webhook → control-plane как CI; gated promotion + branch protection (no bypass); подпись+провенанс ([ADR-0006](adr/0006-model-signing-provenance.md)); **policy-as-code матрица гейтов по критичности** (regulatory/financial → HITL + доп. сканы); HITL-валидация; admission-control на сервинге.
- **Зелёные сценарии:** `SUP-03` (CVE-PR заблокирован), `SUP-04` (подпись), `CI-01`, `REG-01`, `RB-01`, `ACC-02/06/07`, `SC-01`, `VIS-03` (HITL).
- **DoD:** плохой PR не доходит до прода; критичная модель — только после HITL; в прод только подписанное.

### И4 — Рантайм + вывод из эксплуатации
- **Приоритет куратора:** рантайм (T5).
- **Строим:** сервинг 3 моделей разных типов за gateway; rate-limit, extraction-detect, adversarial/FGSM-detect, DoS/DDoS-mitigation, drift; `TOCTOU-01` (ре-верификация подписи при загрузке); decommission-флоу; **петля обратной связи рантайм→реестр** (инцидент авто-помечает версию на ре-ревью / rollback).
- **Зелёные сценарии:** `RT-01/02/05/06`, `DOS-01`, `DOW-01`, `MON-01/03`, `DATA-03/05`, `FB-01`, `TOCTOU-01`.
- **DoD:** extraction/DDoS детектятся; decommission отзывает доступы и снимает endpoint.

### И5 — Карта покрытия + KPI + видимость
- **Приоритет куратора:** видимость (бизнес-запрос лидов).
- **Строим:** `ThreatCoverage`; страница «Карта покрытия» (актив→контроль→угроза→live-статус); [security-KPIs](threat-model/security-kpis.md) (MTTD/MTTR, coverage); CEO-дашборд на реальных данных.
- **Зелёные сценарии:** `VIS-01`.
- **DoD:** карта покрытия живая; CEO видит зелёное, подкреплённое данными.

### И6 — Конвейер + демо одной командой + харденинг
- **Строим:** оркестрация демо-сценариев в один поток (датасет→проверки→обучение→проверки→HITL→gated-деплой→рантайм-атака→decommission); портируемость (ARM+amd64, идемпотентный ре-ран); README-runbook; `SUP-06` (ShadowLogic→ручная валидация) как финальный честный остаток.
- **DoD:** `docker compose up` + одна команда гоняет весь конвейер у проверяющего.

## Глубина, заложенная по итерациям (ответ на «галочка vs глубина»)

| Усиление | Итерация |
|---|---|
| ML-aware SAST-правила + скан ноутбуков | И0 (на своём коде) → И2 (на коде моделей) |
| Схема модель-карты / профиля безопасности | И1 |
| Lineage → анализ blast-radius (импакт-анализ) | И1 |
| Датасет как supply-chain (скан архивов) | И2 |
| Policy-as-code матрица гейтов по критичности | И3 |
| Рантайм → реестр (feedback / авто-rollback) | И4 |
