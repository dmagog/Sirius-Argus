# Sirius Argus — обзор: узлы и защиты

Документ для чтения перед демо: что за система, из каких узлов состоит, какие защиты обеспечивает и от чего. Детали — в [architecture](architecture.md), [risk-register](threat-model/risk-register.md), [bdd-catalog](threat-model/bdd-catalog.md), [adr](adr/).

## Что это

Sirius Argus — слой безопасности и видимости поверх ML-пайплайна. Он встраивает проверки прямо в жизненный цикл модели: от приёма данных и артефактов до вывода из эксплуатации. В прод модель попадает только через единую точку входа (control-plane), где её сканируют, подписывают, проводят через policy-гейт и, для критичных, через ручную валидацию. Каждое действие и каждый отказ пишутся в неизменяемый аудит, а для каждого актива видно, какие угрозы закрыты и каким контролем.

Модели в демо — три НЕ-генеративные (sklearn на наборе iris): бустинг, линейная, anomaly-detection. Домен абстрактный, без привязки к конкретной отрасли.

## Принципы

- **Zero-trust.** Право на каждое действие проверяется на стороне control-plane (Keycloak даёт роль, право на объект решаем сами), любой отказ — в аудит.
- **Fail-closed.** Нет токена или auth-бэкенд недоступен → 401. Неизвестный формат артефакта → блок. Непроверенное в прод не уходит.
- **Защищаем контур контроля в первую очередь.** Если скомпрометирован энфорсер гейтов, все «зелёные» проверки становятся ложью. Поэтому атаки на CI, реестр, сеть и сам control-plane вынесены в модель угроз явно.
- **Finding — сквозная сущность.** Скан моделей, кода, данных, зависимостей и рантайм пишут единую «сработку» с привязкой к активу. Видно расхождение: одна тулза считает чистым, другая — подозрительным; фолз триажится вручную.
- **Defense-in-depth.** Реальные тулзы (modelaudit, model-signing, Semgrep, detect-secrets, pip-audit) объединены с собственными сканерами как baseline; при недоступности тулзы остаётся baseline.
- **Остаток зафиксирован.** Где инструмент не закрывает угрозу, это указано прямо, с компенсацией.

## Узлы системы

Сетевая изоляция в трёх тирах: `edge` — наружу; `internal` (без выхода в интернет) — данные и реестр; `runtime` — изолированный канал serving↔control-plane.

| Узел | Роль | Тир | Защитная значимость |
|---|---|---|---|
| **reverse-proxy** (Caddy) | Единственная точка входа для людей (`:8080`) | edge + internal | Периметр; лимит размера тела (DOS-02); наружу торчит только он и serving |
| **control-plane** (FastAPI) | Энфорсер: zero-trust RBAC, реестр, гейты, аудит, карта покрытия, веб-UI (реестры моделей/данных/решений/акторов + карточки сущностей со сквозной связью актив⇄актор⇄находка) | internal + runtime | Единственный путь к реестру/MLflow; здесь живут все гейты и аудит |
| **MLflow** (обёрнутый) | Backend реестра моделей (версии, теги, стадии) | internal | Наружу не публикуется; пишется только через control-plane (REG-01) |
| **MinIO** (S3) | Артефакты + карантин-стор проверенных моделей (`sirius-quarantine`) | internal | Подпись и verify-on-consume идут по реальным сохранённым байтам |
| **Postgres** | Метаданные control-plane: реестр, Finding, аудит (hash-chain) | internal | Аудит авторитетен и tamper-evident (MON-04) |
| **Keycloak** (+ БД) | OIDC-аутентификация, realm-as-code | internal | AuthN fail-closed (CRED-01/AUTH-01); роль приходит из токена |
| **Redis** | Шина событий + бэкенд rate-limit | internal | EVT-01: действия идут в шину; маскирование секретов в логах (LOG-01) |
| **Vault** (+ vault-init) | Секрет-менеджмент: AppRole, политики, аудит, revoke | internal | Секреты (signing-ключ, service-token) выдаются по политике, не из env (CRED-02) |
| **serving** | 3 НЕ-генеративные модели за рантайм-защитами (`:8001`) | runtime + edge | НЕ на `internal` (RT-06): не достаёт MLflow/MinIO/БД — боковое движение отрезано |
| **observability** (Loki/Grafana/Prometheus) | Метрики и логи (профиль `full`) | internal | `/metrics`, дашборды; аудит отдельно и авторитетно (не путать с observability) |
| **Gitea** | Git + вход для CI (профиль `full`) | internal + edge | CI-01: коммит проходит security-гейт через control-plane (HMAC-вебхук) |

## Карта защит

Контроли сгруппированы по этапу ЖЦ. ID совпадают со сценариями [каталога BDD](threat-model/bdd-catalog.md) — каждый проверяется приёмочным тестом против живого стека.

### Приём артефактов и supply-chain
- **SUP-01** — вредоносный артефакт (pickle-RCE) блокируется на приёме. Скан читает опкоды (modelaudit + собственный genops), `pickle.load` не вызывается — артефакт не десериализуется.
- **SUP-07** — политика форматов по критичности: для regulatory/financial формат с произвольным кодом (pickle) отклоняется, нужен safetensors (convert-or-reject).
- **Архивы** (zip/tar/gz/…) отклоняются — принимаем только одиночный проверенный артефакт, не контейнер с файлами.
- **TOCTOU-01 / SUP-05** — ре-верификация артефакта при загрузке: хэш должен совпасть с зарегистрированным, иначе подмена после скана ловится.
- **SUP-02** (тайпсквоттинг) и **SUP-08** (dependency confusion) — имя-ориентированные эвристики поверх allow-list.
- **SUP-03 / SC-01** — скан зависимостей на известные CVE (своя база ∪ pip-audit); сканируем и собственные requirements (догфудинг).
- **SUP-04** — подпись через OpenSSF model-signing (офлайн-ключ из Vault) над реальными байтами; verify-on-consume на промоушене. Подпись ≠ безопасность: она про целостность и провенанс.

### Код и секреты
- **CODE-01** — ML-aware SAST на код и ноутбуки (собственный AST ∪ Semgrep), код не исполняется.
- **ACC-06** — секрет/токен/ключ в коде → сработка.
- **ACC-07** — захардкоженные бизнес-пороги в условной логике → review-сигнал.

### Промоушен в прод (governance-гейт)
Последовательная policy-матрица по критичности:
- **MON-02** — воспроизводимость (lineage: датасет + commit + env_lock), иначе в прод не уходит.
- **GOV-01** — полнота модель-карты (intended use + limitations).
- **SUP-04** — валидная подпись.
- **VIS-03** (ручной аппрув-гейт) + **ACC-02** (separation of duties) — критичную версию одобряет другой MLSecOps; аппрув привязан к hash артефакта (anti-TOCTOU), а перед решением доступен review-бандл (сработки, карта, lineage, подпись).
- **RB-01** — откат на изъятую/уязвимую версию запрещён.
- **open-critical gate** — незакрытая critical-сработка блокирует промоушен.
- **GOV-02** — принятие остаточного риска: уполномоченная старшая роль (CEO) может провести промоушен при проваленном гейте, но только с обоснованием, условиями и сроком; деплой помечается conditional, всё в аудит.
- **GOV-03** — переход dev→prod атомарен: строка версии берётся под `FOR UPDATE` + state-machine, одновременные запросы не плодят дубль-деплой.
- **MON-05** — непрерывная проверка прода: подпись и целостность прод-версий перепроверяются не только на промоушене, но и пока модель стоит в проде (по сохранённым байтам), подмена после деплоя → critical-сработка.

### Доступ и идентичность
- **ACC-01 / ESC-01** — zero-trust RBAC + object-level авторизация (действие вне роли или чужой объект → 403 + аудит).
- **ACC-04** — допуск к данным по чувствительности (PII/secret), маскирование сэмплов для ролей без допуска.
- **CRED-01 / AUTH-01** — OIDC fail-closed: невалидный/поддельный токен → 401.
- **CRED-03** — brute-force protection в Keycloak: серия неверных паролей временно блокирует аккаунт.
- **ACC-03** — offboarding отзывает доступ субъекта немедленно, не дожидаясь истечения токена.
- **Сервис-аккаунт** (роль Service) — serving ходит в control-plane по pre-shared токену с узким правом, рантайм-петля работает и без dev-режима.

### Рантайм (serving)
- **RT-01** — extraction-детект: бёрст запросов одного клиента → троттлинг + сработка (петля рантайм→реестр).
- **RT-02** — OOD/adversarial-вход помечается моделью аномалий.
- **RT-05** — malformed-запрос смягчён (422), сервис не падает.
- **RT-03/04** — output reduction: API отдаёт категорию, не вероятности → ограничивает membership inference и model inversion.
- **RT-06** — сетевая сегментация: serving не достаёт хранилища (проверено сокетом изнутри контейнера).
- **DOS-01** — распределённый флуд → глобальный load-shedding.
- **DOW-01** — стоимостная квота на тенанта (denial-of-wallet).
- **DOS-02** — оверсайз-загрузка режется по размеру тела (413), не выедая память.
- **MON-01** — дрейф распределения входов → сработка.
- **MON-03** — вывод из эксплуатации снимает деплои.
- **EXF-01** — аномальный объём выгрузок (инсайдерская эксфильтрация) → троттлинг + сработка; счётчик окна в общем Redis (нельзя обойти, размазав по соединениям/воркерам).

### Данные
- **DATA-01** — недоверенный источник → карантин.
- **DATA-04** — PII-маскирование по допуску.
- **DATA-02** (label-flip), **DATA-03** (UGC-бэкдор-триггер), **DATA-05** (train-serve skew), **FB-01** (отравление петли дообучения) — scoped-детекторы качества и целостности данных.

### Секреты, целостность, видимость
- **CRED-02** — секреты в HashiCorp Vault: выдача по AppRole-политике (least privilege), аудит доступа, мгновенный revoke/rotate.
- **MON-04** — целостность аудита: подмена записи рвёт hash-chain, видно в `/health` (detect).
- **LOG-02** — append-only аудит на уровне БД-триггера: UPDATE/DELETE записи отбиваются СУБД, а не логикой приложения (prevent) + якорь головы цепи в шину/Loki. Перепись цепочки скомпрометированным control-plane по DML невозможна.
- **EVT-01 / LOG-01** — шина событий; маскирование секретов в логах.
- **VIS-01** — карта покрытия угроз и CEO-вью на live-данных.
- **VIS-02** — расхождение вердиктов сканеров и триаж фолза.
- **VIS-04** — статус сработки меняет только MLSecOps, с обоснованием и в аудит.

### Единая точка входа в прод
- **CI-01** — control-plane как CI: security-гейт на коммит + HMAC-вебхук Gitea (поддельная подпись → 401) + anti-replay (одноразовый nonce в Redis — повтор подписанного вебхука отбивается).

## Карта покрытия

Контроли и их live-статус видны на CEO-вью `/coverage` (и через `/api/coverage`). Статус «live» означает реальные сработки/блокировки в аудите по этому контролю. На демо карта показывает **32/32 детективных контроля live**. Превентивные и on-demand контроли на карте live-сработок не отражаются — их проверяют приёмочные тесты: output-reduction (RT-03/04), сетевая сегментация (RT-06), fail-closed authN, separation of duties, append-only аудит (LOG-02), атомарность промоушена (GOV-03), brute-force protection (CRED-03), непрерывная ре-верификация прода (MON-05, запускается по требованию/периодически).

Покрытие BDD: **53 из 54 сценариев каталога green** (75 pytest-функций против живого стека) + контроли сверх каталога. Остаётся один — SUP-06.

## Что не закрыто

- **SUP-06** (граф-бэкдоры в весах, ShadowLogic) — статический скан не ловит по своей природе. Компенсация: обязательный ручной аппрув-гейт для критичных моделей + red-team. Это предел инструмента, зафиксированный явно.
- **Целевое** (направление, не реализовано в окне): Trivy/Syft (SBOM), авто-rollback по инциденту, deep-модели, прод-развёртывание Vault (file/raft + auto-unseal). Помечено в [risk-register](threat-model/risk-register.md) и ADR.

## Что смотреть на демо

Один прогон `make demo` против живого стека показывает money-shot'ы:
1. Вредоносная модель → блок на приёме.
2. Уязвимая зависимость → не доходит до прода.
3. Критичная модель → только после ручного аппрува (separation of duties).
4. Extraction в рантайме → детект + троттлинг.
5. Карта покрытия угроз (CEO-вью, 32/32 live).
6. Сквозной ЖЦ одной командой (`make pipeline`): приём→скан→версия→gate→аппрув-гейт→деплой→атака→decommission.
7. GRC: принятие остаточного риска под условиями → conditional-деплой.
8. Vault: секрет по политике → чужой путь 403 → мгновенный revoke.

Запуск: `make secrets` → `DEV_AUTH=1 make up` → `make demo`. Приёмочные тесты: `make test` (сам подсасывает .env; для DOS-02 — `make up-test`).
